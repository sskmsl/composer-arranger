# 保存・起動失敗からの復旧（Issue #224・1番）

曲ごとの最新スナップショットを保持する直列保存キューを追加。進行中の古い書込を追い越さず、未開始の同じ曲の編集は最新へまとめる。失敗した曲は別の曲が保存できても破棄せず、再試行の対象に残す。flushSaveは現在の曲と待機中の全書込の完了/失敗を返す。既存persist呼出しは同期voidのまま、保存失敗は画面へ知らせる。

IndexedDB open失敗を永久にキャッシュしない。曲とlastOpenedを同一transactionで確定後、既存の同期処理へ渡す。起動失敗ではhydratedを終え、既存DBを消さず読み込みを再試行できる。失敗中は新規データを自動保存しない。移行前バックアップの完了も待つ。

保存失敗時は画面の曲を保持し、再試行/JSON退避を用意。保存中または失敗中の離脱はブラウザ標準確認を使う。JSONダウンロードのObject URL破棄は開始後へ遅延。保存スキーマ・生成結果は変更しない。

新規12テスト成功（キュー順序/連続編集/曲を切り替えて戻る保存順、別曲の失敗保持、保存バリア、DB再open、起動失敗と再試行、保存失敗と最新編集の再試行）。全体検証とブラウザ障害注入はIssue224の後続PRで追加して記録する。現時点では実ブラウザの障害復旧を確認済みとは扱わない。

曲を切り替えて戻る条件は、修正前に新規テストが失敗することを確認後、最新編集の曲をキュー末尾へ移す修正で成功を確認。失敗した曲の保持は維持する。

未保存の曲を開き直すときはキューの最新スナップショットを優先する。削除は待機分を除き、既に始まった保存の完了を待ってから行い、削除した曲を後から保存が復活させない。両条件を新規テストで確認する。

## マージ前自動レビューへの対応

編集中の曲を削除した後の復元先も、pendingを優先するloadProjectByIdで開く。未保存の別曲の名前変更は、その最新スナップショットごと同じキューへ置き、非編集中の改名はrecordOnlyでlastOpenedを変更しない。復元時に旧DBで最新編集を上書きしないこと、非編集中の改名が戻らないことを2テスト追加して確認。

保存完了の通知中に追加された編集も、次の書込へつなぎ、flush/discardはその完了まで待つ。再試行バリアの最後の隙間も新規テストで確認する。

再レビューの削除失敗も保護する。削除前に外したスナップショットを返して保持し、DB削除が拒否された場合は、より新しい待機編集がない限りキューへ戻す。非アクティブ曲の削除失敗→再読込→再保存の回帰テストは修正前失敗/修正後成功を確認。キュー/ストアの12件成功、DB再openの既存1件を合わせて13件。

同期完了後のhydrateも、編集中の未保存スナップショットを優先する。DB読込/移行バックアップの待機中に編集された場合も、その編集を古い読込結果で上書きしない。既存同期イベントや通信処理は変更しない。保存失敗後のhydrateと読込中の編集の2テストは修正前失敗/修正後成功を確認（キュー/ストア計14件）。

アカウント切替のP1に対し、保存キュー/未保存編集中の曲をアカウント別に分離する。AuthGateの同期コールバックで切替を同期的に通知し、DB所有者の隔離が済むまで保存/復元を停止。別アカウントのUIへ旧曲を渡さず、元のアカウントへ戻った場合だけ保持編集を再利用する。進行中のDB待機/commit後と遅延クラウド送信にも所有者ガードを置き、切替後に旧処理を再送しない。RPC/認証API/RLS/DB schemaは変更しない。認証通知は同期コールバックで扱う（Supabase公式onAuthStateChange文書を確認）。モックRPC/DBの境界テストと、実IndexedDBの所有者切替を検証する。実アカウント/認証済みクラウド接続は未検証。

復帰時の保存警告は編集中の曲だけでなく、アカウントのキュー全体の未保存有無から復元する。Xだけ未保存→保存済みYを開く→別アカウント→元へ復帰でも、Xの復旧警告/再試行を失わない回帰を追加。
