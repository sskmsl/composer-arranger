# 旋律品質への独立レビューと次の実験案

2026-09-26 / Codex

対象：[PR #166](https://github.com/sskmsl/composer-arranger/pull/166)、コミット `198d1ffa394dc81dfda3f17a6135408d61d912a3`。依頼書、`memorable-melody-research.md`、`composer-principles.md` と生成・選抜・推敲・評価・比較テストの実装を確認した。以下は相談への回答であり、生成ロジックの変更ではない。

**最優先は、新しい作曲規則の追加ではなく、最終MIDIと評価の一致、既存の推敲がHookを弱めていないかの切り分け、少量の盲検試聴である。** Hook-first と、同じ和声上で核を戻す方向には賛成する。一方、「古典に近い」「予想しやすい」を強く最適化すると、利用者の求める「全体を口ずさみたくなる」と別の方向へ進む可能性がある。

依頼書の改善数値は研究メモと照合したが、過去バージョンを含む全コーパス比較は再実行していない。今回新たに実行したのは後述の情報量モデルの小さな再現確認だけであり、聴感上の改善を確認したという意味ではない。

## 1. 現行コードから先に直視すべき点

### 1.1 「作りの良さ」が古典への近さに置き換わっている

`withCraft` の `craftScore` は `classicalLikeness(...).typicality * 100`。Standard / Cinematic / Rhythmic / Minimal の選抜重みは **0.40** で、Standard / Cinematic の Chorus における Hook 0.16、Emotional 0.10、Expectation 0.12 より大きい。さらに選抜後、`refineTowardClassical` が古典モデルの対数密度を上げる方向へ音高を推敲する。[実装：生成・重み](https://github.com/sskmsl/composer-arranger/blob/198d1ffa394dc81dfda3f17a6135408d61d912a3/src/melody-engine/generateFromChords.ts#L636)、[実装：推敲目的関数](https://github.com/sskmsl/composer-arranger/blob/198d1ffa394dc81dfda3f17a6135408d61d912a3/src/melody-engine/classicalRefinement.ts#L41)

これはコード上の事実。ただし、重みだけから聴感への支配力は断定できない。スコアの分散・相関・候補間の差によって実効的な影響は変わるため、各項の寄与と順位変化を記録すべきである。

提案は古典知識を捨てることではない。古典への典型性を「良さ」と同一視せず、**歌として問題のある箇所を見つける参考指標**に戻す実験を行う。重み0.40→0.20→0の比較と、選抜後の古典推敲の有無は別々に試す。古典らしさ97.7→96.3だけでは、品質が下がったとは判断できない。

### 1.2 選抜対象、再生対象、報告値の段階が一致していない

現状には三つの段階がある。

1. `buildCandidate` 内で Hook / Emotional / 理論品質を計算する。
2. `craftNotes` 後の音で古典典型性と Expectation を計算する。一方、選抜へ渡す `notes` や既存の Hook / Emotional 値は前段のものを保持する。
3. 選ばれた3案だけに古典推敲、Hook復元、頂点・呼吸・和声処理を施して返す。`coreRetention`、`emotionalArcScore`、`advancedMetrics` 等は最終音列から再計算されていない。

[候補の仕上げと選抜](https://github.com/sskmsl/composer-arranger/blob/198d1ffa394dc81dfda3f17a6135408d61d912a3/src/melody-engine/generateFromChords.ts#L929)、[返却時の追加推敲](https://github.com/sskmsl/composer-arranger/blob/198d1ffa394dc81dfda3f17a6135408d61d912a3/src/melody-engine/generateFromChords.ts#L1130)

したがって「良い点を取った候補」と「利用者が聴く候補」が同じ状態とは限らない。比較テストでも `candidate.emotionalArcScore` の平均と、最終 `notes` から再計算する `arcParts` が混在する。前者はさらにHookによる係数を掛けた選抜値なので、単純に同じ感情点として比較できない。

まず `coreJudgment / preCraftAssessment / finalAssessment` を区別し、音列ハッシュと評価器バージョンを結び付ける。最終音列の特徴量を再計算し、旧点を最終品質と呼ばない。**全候補へ高コスト推敲を広げる前に、最終推敲を外す案・短い最終候補リストだけ再評価する案を比較する。**

### 1.3 Hookを作った後で、別の方針が繰り返し編集している

`melodicCraft.ts` には、同音連打の変更、跳躍回収、順次進行化、長音の末尾を経過音へ分割、平行完全音程の回避、倚音追加などがある。役割・ロック・サビへの配慮は既にあるが、Hookを保つ処理と動かす処理が交互に走る。[PROFILE_STEPS と処理方針](https://github.com/sskmsl/composer-arranger/blob/198d1ffa394dc81dfda3f17a6135408d61d912a3/src/melody-engine/melodicCraft.ts#L51)

各規則が単独で妥当でも、合成した結果が歌いやすいとは限らない。「同音を直す→滑らかにする→核を戻す→和声に合わせ直す」という編集の往復が、何音起きるかを先に調べたい。

加えて `coreRetention` は選んだCoreそのものへの一致率ではなく `features.hookStrength` である。別の反復が強くなっても高くなり得る。元Coreに対する音程輪郭・発音位置・音価・休符の対応を、許可した移調や語尾変形と分けて追跡する。これは既存 `motifRecognition` と `HookHeadPlan` を使う内部監査で足りる。

### 1.4 反復時の解決先メタデータに確認すべき箇所がある

`repeatOverReturningHarmony` はノートの `startBeat` を移動するが、スプレッドで引き継ぐ `plannedResolution.targetBeat` は移動していない。元ノートに絶対拍の解決先が入っている場合、コピー先に過去の解決時刻が残る。[コピー処理](https://github.com/sskmsl/composer-arranger/blob/198d1ffa394dc81dfda3f17a6135408d61d912a3/src/melody-engine/hookDevelopment.ts#L328)

全候補で発生するとは限らず、聴感上の影響は未確認。ただし「意図ある非和声音を守る」前提に関わるため、掛留・倚音を含む核で解決先も同じ時間差で移ること、後段の和声整合で別の音に直されないことを先に確認したい。

## 2. 数値は何を測っていて、何を測っていないか

### 歌いやすさ・記憶・好みを分離する

| 概念 | 確かめること | 現在の数値だけでは不足する点 |
|---|---|---|
| 発声の容易さ | 聴きながら最後まで無理なく歌えるか | テンポ、連続発声時間、歌い手の音域、難所の連鎖 |
| 記憶・再生 | 少し間を置いて核や続きを歌い返せるか | 音程が歌えることと、音列を思い出せることは別 |
| 認識 | 他の候補と取り違えず識別できるか | 「どこかで聴いた感じ」は正しい記憶とは限らない |
| 好み・採用価値 | この曲に使いたいか、続きを聴きたいか | コード、音色、意図、聴取回数に依存 |

未知旋律の記憶研究でも、珍しい動機は正しい認識だけでなく、条件によって誤った既知感にも関連していた。「珍しさを足すほど記憶が良くなる」という単一の物差しにはできない。[Müllensiefen & Halpern, 2014](https://digitalcommons.bucknell.edu/fac_journ/879/)

録音のHumability 0.80→0.93は、**既知の反例に対して評価器が適切になった**という結果であり、録音や生成音楽の品質が上がった結果ではない。評価器を直すときには、その録音以外の正例・負例を保留して確認する必要がある。

`measureHummability` はBPMを受け取らず、長音の後や十分な隙間の後は `intervalSingability` が任意の跳躍に1を返す。長音は運動準備の余裕になっても、発声中なら息は吸えない。全profileで0.87〜0.98に収まるのは、実際に全て歌いやすい可能性に加え、**指標の判別力が足りない可能性**もある。[実装](https://github.com/sskmsl/composer-arranger/blob/198d1ffa394dc81dfda3f17a6135408d61d912a3/src/melody-engine/hummability.ts#L31)

ただし、差を出すためだけに減点を厳しくするのは逆効果。現段階で選抜に加えず、難所を見つける補助指標にしている判断は妥当である。

### 情報量には具体的な較正上の課題がある

**良い点：** `build_expectation_model.py` は曲単位で5分割して学習曲と較正曲を分けている。同じ曲の窓を無作為に混ぜた単純な学習漏洩ではない。

**確認・改善点：**

- 較正は最初の発音から **32四分音符拍** ごとの窓で短期モデルをリセットする。一方、実行時は候補全体を一度に評価する。4・8・16小節を同じ分位点へ当てると、長さと短期学習量が混ざる。32拍は4/4なら8小節だが、他の拍子では一致しない。
- 現モデルは「前音の主音からの半音クラス＋直前音程の粗い分類→次の音程」の長期・短期頻度であり、2小節の核の順序を直接覚えるモデルではない。反復による情報量低下を、そのまま人のモチーフ認識量と解釈しない。
- 音価・休符・拍節位置・コード・BPMは確率計算に入らない。リズムを壊しても同じ音高順なら同点になり、コードを変えても同点になる。
- 曲単位の分割に加え、同一曲の異版、窓数の多い曲の過大寄与、音数・調・拍子の偏りを点検する。`extract_openewld.py` は調を旋律から推定し、タイ結合・反復記号の展開を明示していない。実際にどの程度分布へ影響したかはデータ確認が必要。
- 5分割較正モデルは約80%の曲で学習、配布モデルは全曲で学習する。これは普通の運用だが、分位点の安定性を別途確認する。

[較正コード](https://github.com/sskmsl/composer-arranger/blob/198d1ffa394dc81dfda3f17a6135408d61d912a3/tools/melody-reference/build_expectation_model.py#L91)、[実行時モデル](https://github.com/sskmsl/composer-arranger/blob/198d1ffa394dc81dfda3f17a6135408d61d912a3/src/melody-engine/expectation.ts#L38)、[抽出コード](https://github.com/sskmsl/composer-arranger/blob/198d1ffa394dc81dfda3f17a6135408d61d912a3/tools/melody-reference/extract_openewld.py#L20)

今回、配布JSONの人工的な `selfCheck` とPythonの `Counts.information` を用いて確認した。自己検査値との一致を確認したうえで、同じ人工音列を16拍間隔で繰り返すと以下になった。

| 配置枠 | 音数 | 平均情報量 |
|---|---:|---:|
| 16拍・1回 | 9 | 2.138930 |
| 32拍・2回 | 18 | 1.654226 |
| 64拍・4回 | 36 | 1.202409 |

同じ音高順を保って全発音位置・音価を変更した場合、各音の情報量は完全に同じだった。これはモデルの設計どおりであり、音楽的な優劣の実験ではない。ただし、窓長を揃えず分位点を比較できない理由と、リズム品質をこの点数で代用できない理由を再現している。

まず32拍窓・同じリセット条件で比較し、短い候補は別較正または参考値扱いにする。曲全体の短期学習を評価したい場合は、曲全体で較正した別集計として明示する。

### 分布への近さは目標値そのものではない

歌のQ25〜Q75は「そのコーパスによくある値」であり、「人が最も好きになる範囲」の実測値ではない。現在の点数は中央を1、低情報量側を最低0.85、高情報量側を0まで下げる非対称な形で、論文の逆U字を直接再現したものでもない。過度な予想外さを抑える仮説的な重みとして扱うべきである。

同様に、完全反復6%を達成したことは分布差が縮まった証拠であり、最適な反復量を発見した証拠ではない。「情報量差の残りは反復が原因」という説明も、短期モデルの有無の比較だけでは因果的な寄与分解にならない。音の選び方と短期更新は相互作用する。

平均だけでなく、フレーズ別の値、局所的な高情報量の連続、Core再提示での変化を記録する。ただし記録した全項目を選抜点へ加算しない。

## 3. Claudeの8案への回答

### 1：聴いた評価を集める――賛成。ただし学習機能は後

最優先群に入れる。ただし初手は大きな評価UIや自動学習ではなく、12組程度の盲検比較と小さな評価記録でよい。「好き」「再生できる」「コードと合う」「採用したい」を分け、同点・両方不採用も許す。理由タグは選択後に記入し、先に見せて誘導しない。

利用者の耳はこの製品の目標を決めるが、一回の回答を誤差ゼロの教師データとはしない。聴取順、音色、音量、慣れ、疲れ、曲の目的を記録する。

Bradley–Terryの候補固有の強さを推定するだけでは、未聴取の新規候補の重みは学べない。後で行うなら、候補間の少数の特徴量差から選好を予測する正則化モデルとし、曲・セッションを跨ぐ保留評価で固定重みを上回るか確認する。数十件で多数のprofile・ジャンル別重みを学ばせない。[Bradley & Terry, 1952](https://academic.oup.com/biomet/article-abstract/39/3-4/324/326091)

### 2：3案を予想しやすさで散らす――優先度を下げる

現状すでに品質0.6／多様性0.4、冒頭・構造・DNAの多様性条件がある。さらに三つの情報量帯を必須にすると、良い候補を捨てて帯を埋める可能性がある。まず採用可能な候補内での弱い多様性軸にとどめる。「定番／冒険」という表示名も、指標の妥当性確認前には付けない。

Gold et al. は個人差を示すが、好みの幅と熟達度の関係はStudy 1のGold-MSIで見られた結果で、Study 2の経験年数等では有意でなかった。固定の3帯や「経験者は必ず好みが狭い」を保証しない。同研究は情報量だけでなく不確実性も扱う。[Gold et al., 2019](https://www.marcus-pearce.com/assets/papers/GoldEtAl2019JNeuro.pdf)

### 3：驚きの置き場所――構造に依存させるなら賛成

「3小節目以降の最大情報量」に固定しない。冒頭の特徴的な跳躍がHookそのもので、その後の反復で馴染む場合もある。問うべきは、聴き手が何を予測できる状態で、どの予測を一度だけ変えたかである。

Slobodaは83人の質問紙と報告された反応箇所の分析であり、倚音を置けば感動する、3小節目から驚かせるべき、という因果実験ではない。[Sloboda, 1991](https://journals.sagepub.com/doi/10.1177/0305735691192002)

実験は「同じCoreの反復後、語尾だけ変える」対「変えない」。同じ平均情報量でも変化位置だけを変える対照も作る。最大値の位置を点数化して自分で最適化するだけでは不十分。

### 4：リズムの予想しやすさ――方向は賛成、シンコペーション目標の根拠を修正

IOIだけでなく開始拍、拍節の強弱、音の保持、休符、フレーズ境界との関係を扱う。Witekの対象はファンクのドラムブレイクに対する快さ・動きたさであり、歌唱旋律の記憶や歌いやすさの最適シンコペーション量ではない。[Witek et al., 2014](https://pmc.ncbi.nlm.nih.gov/articles/PMC3989225/)

独立した「リズム複雑度」を上げるより、Coreの発音位置と語尾の長短が後段で保たれているかを先に調べる。音高とタイミングの期待を共に扱う研究は、この方向の手がかりになるが、特定の重みを保証するものではない。[Sauvé et al., 著者公開稿](https://arxiv.org/abs/1708.03687)

### 5：現代ポップスの物差し――補助として賛成、データ追加は後

年代だけでコーパスの有用性を決めない。まずタイ・弱起・反復展開・フレーズ区切り・調推定・拍子・音数の定義を揃える。定義の異なる論文の平均値を、そのまま既存閾値へ混ぜない。

公開論文から知見を得ることと、論文が使った楽曲データを製品学習へ利用することは分ける。新規データの権利・来歴の条件は今回の制約を維持する。最初の補強データは、利用者が生成候補をどう選ぶかの評価記録で十分に価値がある。

### 6：Verseは自由、Chorusは和音と一体――条件付き採用

Temperleyの議論はロックの特定の状況、特に五音音階的旋律等に関するもので、全ジャンルの必須規則ではない。[Temperley, 2007](https://www.cambridge.org/core/journals/popular-music/article/abs/melodicharmonic-divorce-in-rock/33D93CFAE1EDBC800B86318078D35F7C)

実装するなら「サビをコードトーンへ寄せる」より、フレーズの到達点で旋律・ベース・和声変化がどう一致するかを扱う。同じCoreがコード変化で別の役割を得る場合は維持する。長音の主和音寄せが効かなかった結果を尊重し、似た修正を名前だけ変えて再導入しない。

### 7：跳躍後の回収を弱める――ジャンル一律より局所条件

von Hippel & Huronの中心的な論点は、跳躍後の反転が音域端への接近・音域制約で説明できること。依頼書の「古典で強く、ロックで弱い」という具体的比較を、この論文だけの結論として扱うのは避け、別の追試を明示すべきである。[von Hippel & Huron, 2000](https://online.ucpress.edu/mp/article-abstract/18/1/59/62088/Why-Do-Skips-Precede-Reversals-The-Effect-of)

「前の跳躍が大きいから必ず戻す」から、「音域端、次の到達音、音価、Coreの識別性から戻す必要があるか」へ変える実験を支持する。参考曲の0.18だけを目標にせず、跳躍の閾値、回収までの音数、休符を跨ぐかを揃える。

### 8：予想しやすさを生成へ使う――最後に小さく試す

候補に良い案が存在しないなら必要になる。ただし、局所的に出現確率が高い次音を選び続けても、良いフレーズにはならない。選抜と同じモデルで生成も評価すると、指標への適合だけが急速に進みやすい。

試すならCoreの候補生成の弱い事前傾向、または語尾の数候補の比較に限定し、リズム・Coreの識別部分・許容音域を先に守る。期待モデルは人の聴取を説明するモデルであって、品質保証器ではない。[Pearce & Wiggins, 2012](https://onlinelibrary.wiley.com/doi/10.1111/j.1756-8765.2012.01214.x)

「AI生成曲が口ずさみやすいのはこの学習のおかげ」という説明は、モデル・学習データ・比較条件を確認していない仮説のままにしておく。

## 4. 独立した施策案

以下の実装案・数値は、論文がそのまま検証したルールではなく、このコードへの提案である。

### A. 「足す前に、既存の修正を減らす」実験

同じ未推敲候補を固定し、①古典推敲のみ無効、②同音連打変更のみ無効、③経過音の挿入のみ無効、④跳躍回収のみ条件化、を別々に比較する。候補選抜を固定した比較と、再選抜を許した比較を混ぜない。

測定は元Coreへの対応率、変更・挿入・復元された音数、リズム保持、和声上の未処理解決、そして盲検の採用選択。「何もしない」が同等以上なら処理を減らす。反復を作曲の有効な道具として扱う実務にも合う。[Berklee：Writing Melodies](https://online.berklee.edu/takenote/simple-tools-for-better-melodies/)

### B. 生成の失敗と選抜の失敗を分ける

3案だけを聴いて生成器を変更しない。少数の条件で候補プールから、選ばれた案と選外の案を匿名で比較する。

- 選外に採用したい案が多い：先に候補評価・多様性条件を直す。
- プール全体が弱い：Core生成・展開に手を入れる。
- 推敲前が良く、最終だけ弱い：仕上げを直す。

主指標は「3案の中に採用可能なものが一つ以上ある割合」と、候補プール内の利用者の好みを最終3案が拾えた割合。これは新規研究指標ではなく、製品としての失敗箇所を特定する診断である。

### C. 音程より先に「歌の言い回し」を固定する

Coreの開始拍、アクセントとなる長音、語尾、休符を一つの句として保持し、その句の中で音高を選ぶ。歌詞がない現段階では本当の言語的prosodyを測れないので、仮の発話単位として扱う。日本語の歌を想定する場合も英語の強勢をそのまま転用しない。

Berkleeの旋律講座はリズム、句の長さ・余白・開始と終わりから入り、同じリズムで形を変える、コード変化を跨いで連続性を保つ手法を扱う。これを既存CoreとPhrasePlanへ適用する案であり、リズム素材集を追加する必要はない。[Kachulis：Songwriting: Melody](https://online.berklee.edu/courses/songwriting-melody)

同じ音高列でリズムだけ異なる候補、同じリズムで音高だけ異なる候補を比較し、どちらが現在の品質を制限しているか調べる。発音・休符の位置が自然に思い出せるか、BPMを変えたときに歌唱の負荷が急増しないかを確認する。

### D. 語尾・接続を少し先に見てから中間音を決める

各音を順に選んだ後で全体を直す代わりに、既存のフレーズ役割から「開いた語尾／保留／帰着」を決め、末尾1〜2音と次のCoreの入口を少数候補で比較する。固定の終止形や毎回の主音着地にはしない。Coreの頭を固定し、まず語尾だけを検討する。

句は休み、保持、リズム的・調的な着地によって区切られるという作曲実務を、局所的な先読みへ落とす提案である。[Perricone：Melody in Songwriting の公開抜粋](https://online.berklee.edu/takenote/conjunct-disjunct-melody-basic-definitions/)

評価は最終音単体の安定性より、句を跨いだ跳躍・発音密度・未解決音の行き先・回答感。試聴では、頭の記憶だけでなく、後半も途切れず口ずさめるかを確認する。

### E. 同じ核のまま和声的意味が変わる案を残す

今の反復はコード記号列の一致を条件にしている。次段階では、同じコードでなくても、保持音・許容された緊張音・意味ある解決として成立するかを少数候補で判定する。まず「変更なし」と「末尾1音だけ変更」を比較し、全面的なコード追従を避ける。入力コードそのものは変えない。

和声の期待研究でも驚きと不確実性の相互作用が扱われており、単純な不協和量だけで快さを表せない。ただし和音系列の実験を、そのまま旋律の採点式にはしない。[Cheung et al., 2019](https://pubmed.ncbi.nlm.nih.gov/31708393/)

測定は異なる和声上でのCore保持、緊張音の持続と解決、盲検での「コードに合う／同じ核が別の表情になる」。無条件の再利用は採用しない。

### F. セクション単体の山を、曲全体の山と区別する

全セクションをそれぞれ後半ピークへ寄せるだけでは、Verse→Pre→Chorus全体で高まりすぎたり、同じドラマが続く可能性がある。既存Section Contextを使い、同じCoreのVerseとChorusを連続再生して評価する。音高・音数を上げる以外に、語尾を長くする、休符を広げる、和声との着地を一致させる候補を比較する。

これは既存の感情弧を捨てる案ではなく、局所最適を曲全体で確認する案。安定・不安定を曲の意図に合わせて扱う作曲判断が参考になる。[Pattison：Prosody in Music and Songwriting](https://online.berklee.edu/takenote/prosody-in-music-and-songwriting/)

## 5. 優先順位と採否の測り方

| 順位 | 実施内容 | 同条件の比較 | 採否を決める証拠 |
|---|---|---|---|
| P0 | 最終音列と評価の一致、反復時の解決先、窓長の統一 | 同じMIDIを同じ評価条件で再採点 | ハッシュ・メタデータ・評価段階の一致。音楽的改善とは別の正確性確認 |
| P1 | 小規模な盲検評価、プール内の取りこぼし診断 | 同じ曲条件、匿名候補、音色・音量統一 | 採用率、選外候補への敗北、回答の再現性 |
| P1 | 古典推敲・同音修正・挿入等の一要素ずつの除去 | 同じCore・同じ未推敲候補 | Hook保持と和声安全性を保ち、採用選好が改善するか |
| P2 | 歌の言い回しと語尾の先読み | 同じCore、リズムのみ／語尾のみを変更 | 後半の歌い直し、句の自然さ、局所的な難所 |
| P2 | 驚きの位置、別和声上での核保持 | 同じCore、変更箇所1か所 | 意外性の意味、和声適合、記憶と採用価値 |
| P3 | 聴取評価から少数の重みを学ぶ | 曲・セッション単位で保留 | 未聴取候補で固定重みより選好を予測できるか |
| P3 | 情報量による候補多様化、現代統計の補助 | 同じ候補プールで再選抜 | 最終3案の採用率が上がるか。帯が散っただけでは採用しない |
| P4 | Expectationを生成へ弱く導入 | 同じ予算・Core条件・seed群 | 保留条件の採用率、識別性、速度。情報量低下だけでは採用しない |

P1の試聴準備とP0の監査は並行できる。評価UI完成まで音楽の検証を止める必要はない。

### 比較プロトコル

1. **機構の比較と製品の比較を分ける。** 前者は同じCore／候補プールを固定し一処理だけ変える。後者は同じ入力から最終3案を生成し、再選抜込みで比べる。乱数消費が変われば同じseedでも同じCoreにならないため、Coreのハッシュを確認し、必要なら段階別の乱数系列を分ける。
2. 最初はStandard、4進行×3役割（Verse / Pre / Chorus）×2長さ（8 / 16小節）×4seed＝96条件を一例とする。Tempo / Genre / Rangeを固定し、Cinematicと低速・高速条件は別検証にする。最後に未調整の進行・seed群で確認する。これは検出力を保証するサンプル数ではない。
3. 最終MIDI、入力、Core・音列ハッシュ、候補の出自、評価器バージョン、各処理の変更量、処理時間を残す。集計はprofile・役割・長さ別。平均だけでなく悪化件数と下位群も見る。
4. まず短い試聴を1日12組程度、複数日に分ける。A/B順は無作為化、同点／両方不採用を許可し、少数の重複ペアで判断の安定性を見る。好みの比較は伴奏付きで行い、問題の切り分けに旋律単独版を使う。
5. **記憶テストは選好A/Bと分ける。** 似たA/Bを続けて聴くと記憶が混ざる。各試行では片方だけを一定回数聴き、短い別作業の後、核と後半を歌い直す。条件を曲ごとに割り当て直して比較する。絶対音高のずれと、輪郭・リズム・欠落を分けて判定する。発声が難しければ再認も補助にするが、歌い直しと同じ指標とは呼ばない。
6. 主指標を「採用可能な案を含む3案セットの割合」、副指標を再生・記憶、和声適合、Hook保持に置く。情報量・古典典型性・内部感情点は説明変数とする。
7. 同じ曲・seedから出た3案や各音を独立標本として数えない。差と不確実性は曲条件をまとめた単位で報告する。少量の試聴は探索と位置付け、僅差を改善と断定しない。初回のばらつきを基に、追加確認の量と許容悪化幅を先に決める。

**採用しない基準：** 最適化した内部点だけが上がる／記憶が良くても採用したくない／Hookが残ってもコードに合わない／一部の好条件だけ改善／生成時間が許容範囲を超える。効果不明は保留し、失敗も結果として残す。

## 6. 実装時の危険と抑え方

| 危険 | 具体的な対策 |
|---|---|
| 全候補への重い推敲で遅くなる | `refineTowardClassical` は既定で最大5周、編集可能音ごとに最大8音高を全体採点する。単純実装では音数に対して概ね二次的に重くなる。まず除去・小さい最終候補集合での再評価を試す |
| 候補評価を足すほど待ち時間が増える | 既存プールは最大27案、3案組は最大2,925組。特徴量は各候補で一度だけ計算し、組合せ評価内で期待モデルや全体推敲を呼ばない |
| staleなキャッシュ | pool indexだけでなく最終音列ハッシュ・評価器バージョンを使う。編集・候補差し替え後に評価を使い回さない |
| Hook-firstが後段に負ける | Coreの音高だけでなくリズム・休符・アクセントの由来を追跡。元の核への対応と一般的な反復量を別にする |
| 既存閾値が誤った目的を固定する | `developmentPrinciples.comparison.test.ts` の古典らしさ94以上、内部Hook点等は回帰検知用であり、聴感の真理ではない。実験中は旧値も報告し、失敗を消すために閾値を下げない。外部評価で採用を決めた後、意味を説明して更新する |
| 同じ指標で生成・選抜・成功判定する循環 | 変更した指標の改善と、独立した試聴・再生結果を別表にする。既存の「改善した場合のみ採用」ゲートによる無悪化は独立検証と呼ばない |
| 相関した評価の二重加点 | Hook、反復、情報量、古典典型性の候補間相関と順位寄与を調べる。合成重みの総和が1を超えないことも検査する（現在の個別上限を全て使うと1.06になるため、将来拡張時に注意） |
| 少数の好みへの過学習 | 特徴量・自由パラメータを絞り、評価日・曲条件を跨いで確認。新しい基準で良かった候補だけを学習し続けない |
| 長い・珍しい音が点稼ぎになる | 最高音や倚音の有無ではなく、文脈と一度の役割を判定。既存の「何もしない」候補を必ず残す |

速度はブラウザの代表端末でp50 / p95、最大プール、長いセクションを測る。新案の速度は今回未測定。許容秒数を固定してから、例えばp95の増加10%以内を初期の実験予算にする。ただし既に数秒を超えるなら、相対値より絶対時間の改善を優先する。

既存比較テストは4進行・3seed・Verse/Chorus・Standard/Cinematic・一つのsongProfileを中心とする。テンポを明示した比較やPre-Chorus、未知の進行も必要であり、このテストの成功を全profileの音楽品質へ一般化しない。[比較テスト](https://github.com/sskmsl/composer-arranger/blob/198d1ffa394dc81dfda3f17a6135408d61d912a3/src/melody-engine/developmentPrinciples.comparison.test.ts)

## 7. 調査メモの表現も修正したい

- 「涙を誘うのは倚音」→「報告された涙の箇所に倚音等が見られた」。処方箋と観察結果を分ける。
- 「動機は短く、1つだけ珍しく」→「記憶に効く特徴は課題と比較対象に依存する」。珍しい要素を必須にしない。
- 「8小節ごとに反復1回まで」をNunes et al.から直接導いたように書かない。同研究の中心は歌詞の反復と流暢性・市場成果であり、このMIDI反復上限はアプリ側の仮説である。[Nunes et al., 2015 著者公開版](https://www.francescavalsesia.com/uploads/1/0/5/1/105151509/the_power_of_repetition_jcp_2015.pdf)
- 反復の有効性を示す実験も、素材と聴き手の条件が限定される。反復を許す理由にはなるが、全作品に共通の反復率を与えない。[Margulis, 2013](https://collaborate.princeton.edu/en/publications/aesthetic-responses-to-repetition-in-unfamiliar-music/)
- 情報量モデルを「IDyOMと同等」と解釈しない。現行の低次統計モデルが何を条件にしているか、何を省いたかを明記する。

## Claudeへ渡したい最初の実装単位

**第1段階：評価の正確性。** 最終音列とスコアの対応、較正窓、反復の解決先、処理段階の変更履歴を確認する。ここでは新しい美的スコアを増やさない。

**第2段階：既存処理の除去比較。** 同じ候補を固定し、古典推敲・同音修正・経過音追加を一つずつ外して試聴する。選外候補も少数含め、作る能力と選ぶ能力を分けて調べる。

**第3段階：弱点が分かった箇所だけ改善。** リズムの言い回し、語尾・接続、和声を跨ぐ核の保持から一つ選び、同じCoreで比較する。期待モデルを生成へ広げるのは、その後でよい。

目標は採点項目の多い生成器ではなく、**耳で選びたい候補を作り、その良さを仕上げで失わず、最終3案へ残せる生成器**である。
